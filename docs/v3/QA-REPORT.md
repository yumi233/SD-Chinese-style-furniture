## 自动化验证与复现

### 对原结论的更正

原 `475f7a4` 报告中的 **107/107 是某一次执行的观察值，不是稳定性证明**。负责人在该提交上两次重跑失败；本轮在保留负责人两项改动的 `ef324c1` 上，也直接复现了 `iphone: single result...` 的卡片数量 `1 !== 2`。因此撤回原文将一次通过表述为已可靠完成验收的结论。

### 真实原因与修复

不稳定由测试同步问题与产品恢复缺陷共同造成，不能仅靠延长等待时间处理：

1. **旧等待条件会提前成立。** 原测试的 `idle()` 只看 `busy=false`，`ready()` 只看任意选中图片可读。刷新时历史先返回旧版本，任务查询仍在进行，这两项已同时成立。测试会提前断言卡片数量。它也可能提前开始框选；从 `render()` 会重建卡片并清除框选的实现可知，后续步骤也会受这个未完成任务影响。原测试点击停止后还立即刷新，未确认停止请求已经被服务端接受。
2. **产品把旧快照缺少新记录误判为删除。** 恢复顺序是读取历史 → 查询活跃任务 → 读取已保存任务。如果生成在历史快照之后完成，活跃列表为空，任务详情已是 completed，但先前的历史快照没有新记录；原代码于是清掉任务指针、丢弃结果。可控复现中，桌面与 WebKit 均出现「服务端 2 条记录，页面长期只有 1 张卡片」。修复为：观察到终态任务后重新读取最新历史，再判断记录存在或已删除；保留跨账号 epoch 校验。
3. **首页描述被刷新重复消费。** 真实的新描述必须优先于旧终态任务，但已经带入的 `?prompt=` 原先一直留在地址栏；完成任务后刷新会再次进入“新作品”分支，清空画布。首页描述现在只消费一次：带入后用 `replaceState` 移除该参数、保留其他参数及 hash，应用描述或采纳任务后也清空内存中的交接值。

测试改为捕获创建响应中的 **task ID**，确认停止响应的 `stopRequested=true`，再等待该 task 的终态及其 `historyRecord.id` 对应的选中卡片、图片解码与准确数量。夹具通过显式放行的 Promise 控制出图与任务查询时机，不再靠 2600/1800ms 的模拟延迟制造刷新窗口，也没有加长 sleep。文字切换等待实际文案，而不是等待固定 100ms。

每个浏览器新增三项回归：延迟恢复时不能把旧卡片当新结果；在历史快照与任务查询之间完成时仍恢复新结果；真实删除终态记录后刷新不能复活它。分别精确检查 3→4→5 张卡片及删除后回到 4 张，任务 POST 和模拟图像调用均为每端 5 次，防止刷新重复提交或停止后多发一轮。失败时保存首个失败状态并跳过依赖步骤，避免把连带错误误判成多个独立缺陷；最终成功记录必须无跳过。
