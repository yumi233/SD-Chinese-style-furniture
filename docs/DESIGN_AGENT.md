# 设计智能体：需求、方向、参考、生成与评审

木生的生图不再是“一段提示词换一张图”，而是一条可追溯的设计流程。每一步的结果都会保存：锁定了什么需求、用了哪些参考、选了什么方向、改了什么、评审依据是什么。

```text
理解需求 → 锁定需求 → 检索参考 → 确定方向 → 生成 → 逐项评审 → 定向修改 → 保存版本
```

工作台进度只显示真实阶段：整理需求 → 选择参考 → 生成图片 → 检查方案 → 保存结果。后端任务的 `phase` 依次是 `brief`、`references`、`generating`、`reviewing`、`saving`。界面不显示假百分比。

## 1. 设计需求（brief）

`src/design/brief.js` 把用户的中文或英文描述整理成结构化需求：

| 字段 | 含义 |
| --- | --- |
| `requirements` | 必须满足：家具类型、材料、需要的构件、颜色、人数、尺寸 |
| `prohibitions` | 禁止出现：用户写明的，以及由它推出的（`origin: "derived"`，`because` 记录原因） |
| `styles` | 风格偏好：用户写明的（`source: "user"`）和面板预设（`source: "preset"`） |
| `openAreas` | 可以自由发挥的部分，如材料组合、颜色、细部 |
| `references` | 本次使用的参考及用途 |
| `assumptions` | 自动补全的假设，如“未写尺寸，按常规餐椅尺度” |
| `conflicts` | 互相矛盾的地方 |

**优先级**：用户明确要求 > 本任务锁定方案 > 参考案例 > 风格预设 > 模型自由发挥。提示词、负面提示词和参考说明都按这个顺序检查冲突，低优先级的内容一旦与高优先级冲突就被去掉，并在结果面板“已去掉”里列出。

例：“一把无扶手的新中式餐椅，全金属，不要木头”

- 必须：家具类型 餐椅；材料 全金属
- 禁止：木材；扶手；圈椅式椅圈、官帽椅形制（由“扶手”推出）；竹、藤、石材、玻璃、软包坐垫、织物、皮革（由“全金属”推出）
- 风格：新中式（预设）

否定词的作用范围只到它修饰的概念：“无扶手”“不能像圈椅”“不要木头”“armless”“without wood”都会进入禁止项，而不是被当作正向关键词写进提示词。“木生”“石大宇”这类含材料字的专名不会被误判。

**澄清**：只有核心矛盾才打断用户，例如“无扶手的圈椅”（圈椅本身带扶手）。这时任务返回 422，`details.clarification` 列出冲突项，前端给出选择按钮；用户选择后以 `conflictResolution` 重新提交。非核心的不确定之处记为 `assumptions`，不打断。

**继续细化时的新要求**：新要求对它提到的概念覆盖旧要求。“全金属”之后说“坐垫换成黑色皮革”，皮革和坐垫从禁止项移到必须项，“全金属”收窄为“除软包坐垫、皮革外全金属”；其他禁止项（木材、扶手……）保持不变。“这把椅子”只是指代，不会改掉家具类型；只有“改成/换成……”才会。

## 2. 设计方向（direction）

`src/design/direction.js` 根据需求确定一个方向，并保存在设计会话里：

- 风格与配比（`modernity`）。需求里写明的风格优先于面板预设：选着“新中式”写“宋式书桌”，方向使用“当代宋式”，并在说明里写明原因。
- 中式特征从哪里来：可以是一种传统手法（作为可选的点睛，以形体和比例转译），也可以只靠比例、线条和留白（`expression.kind = "proportion"`），传统符号不是必需的。
- 形体手法、风格包配方、材料（用户指定的材料优先，其次风格包材料，再次默认推荐）。
- 已排除的手法：与禁止项冲突的条目不会被选中，例如无扶手时不会选“一笔连续的椅圈线”。

方向由需求原文决定（稳定哈希），同一需求重复生成得到同一方向和同一提示词。三个按钮：

| 操作 | 方向 | 输入图片 |
| --- | --- | --- |
| 生成另一个版本 | 保持方向，只改一个受控变量（机位与光线、比例细节等） | 无 |
| 探索新方向 | 重新选择，排除上一个方向的手法与形体手法 | 无 |
| 继续细化 | 保持方向，只改用户写明的范围 | 上一版图片 |

用户没有想法时，`POST /api/v1/design/directions` 给出三个明显不同的方向：最匹配需求的方向（默认）、一个风格包方向、一个只靠比例的方向，并附上匹配的真实案例。

**当代宋式**（`styleProfiles.js` 的 `song`）是独立方向：清瘦圆润的构件、素面、夹头榫、灯挂椅式靠背、编织坐面等（`src/knowledge/song.json`），负面词排除明清复制品；评审同样检查古旧风险。

## 3. 提示词组装

`src/design/composer.js` 每次都从需求和方向重新组装提示词，不在上一版提示词上叠加，因此“重新生成”与 Codex 收到的设计线索一致。顺序：

1. 用户原文
2. `locked requirements (highest priority, override any style preference): …`
3. 风格锚点与配比（与禁止项冲突的部分去掉）
4. 传统手法（可选点睛）或比例说明；形体手法；风格包配方；材料
5. 文字模型的草稿（若启用，去掉与禁止项冲突的句子）
6. 受控变量（另一个版本）
7. 本版修正（评审给出的最多 3 条，违反需求的优先）
8. 细化范围：`edit the attached previous version: change only …; keep everything else unchanged, including …`（保留清单只列这类家具有、且没被禁止的部件）

负面提示词合并风格反向词和禁止项，并去掉与必须项冲突的词。Codex CLI 另外收到同样结构的 `styleGuidance`；参考资料里的文字放在 `referenceNotes`，明确标为不可信的参考数据。

## 4. 参考库

### 分类

| 类别 | 内容 | 位置 |
| --- | --- | --- |
| 真实案例 | 当代中式与宋式灵感的桌椅凳，附出处 | `src/references/realCases.json` |
| 材料与工艺 | 知识条目里的材料、构造、尺度 | `src/knowledge/*.json` |
| 设计经验 | 没有外部出处的归纳，标为“经验” | `src/knowledge/*.json`（`evidence: "heuristic"`） |
| AI 概念图 | 风格包参考图，标明“AI 生成，不代表真实产品、材料或工艺” | `STYLE_REFERENCE_DIR`（私有） |

### 真实案例

每个案例记录：出处（https）、设计师与品牌、年份、类别、风格、材料、尺寸、结构、参考价值、适用范围、未知项和可用于哪些用途。**每一条材料和尺寸都标明依据**：`source`（出处写明）、`visible`（图片可见）、`inferred`（推断）、`unknown`（未知）。图片只给链接（`imagePolicy: "link-only"`），不复制进仓库；6 件历史藏品中 5 件为博物馆 CC0 开放授权，只用于知识整理，不作为生图参考。

当前规模：43 个当代案例，其中坐具 31、桌 8、长凳 3、凳 1；标为宋式灵感的 8 个；材料依据 42 条来自出处、1 条推断、8 条未知；只有 10 个案例的尺寸有出处确认；来源涉及 30 个网站。**缺口**：宋式专属的当代案例很少；桌类偏少；多数案例缺少可确认的尺寸。不确定的中文名称、产地没有写入，没有编造案例。

匹配（`matchCases`）只用关键词和元数据：同一家具类别 +4、同风格 +3、含必须材料 +2。案例材料与本次禁止项冲突时，只保留轮廓与结构用途，并注明原因。

### 用户上传

- 图片：PNG / JPEG / WebP，≤ 5 MB，校验文件头。文档：txt / md ≤ 200 KB，PDF ≤ 6 MB（只校验格式，暂不解析内容）。每个账号最多 60 份。
- 用途：轮廓、材质、结构、氛围。上传后按文件名自动标注材料与用途，用户可改；改过的标注记为 `annotation.source: "user"`。
- 按账号隔离：存放在 `USER_REFERENCE_DIR/<账号 ID 的 SHA-256 前缀>/`，其他账号读不到、用不了。上传内容不会进入公共库。
- 上传的图片和文档里的文字只作为参考数据，不作为指令执行。
- 冲突处理：参考图的材质与禁止项冲突时，去掉“材质”用途，只保留其他用途；没有剩下的用途就不使用，并在结果里说明。

每次最多附 3 张图：继续细化时上一版图片排第一，其后是用户上传的参考图，剩余名额给风格包的 AI 概念图。真实案例只给链接，以文字说明它贡献的轮廓或结构，不发送图片。不支持参考图的引擎只使用文字说明。

## 5. 评审

`src/design/evaluation.js` 按四项标准评审，每项为通过 / 不通过 / 无法判断，并附视觉证据：

| 标准 | 检查 |
| --- | --- |
| 需求 | 逐项核对必须项与禁止项（不可见的尺寸记“无法判断”） |
| 风格 | 是否符合方向；古旧风险（`antiqueRisk`）；是否只换了材料 |
| 合理性 | 可见结构是否连续、可成立 |
| 一致性 | 细化或三视图时，与上一版是否一致；列出未要求的改动 |

规则：

- **违反需求不能靠高分抵消**：有违反项时最高 60 分，风格不通过最高 70 分；结论为“需修改”或“不通过”。
- **字段缺失即评审不完整**：缺少风格检查、古旧风险或（有上一版时）一致性，结论为 `incomplete`，不判通过。
- 修正建议最多 3 条，违反需求的排在前面，例如“完全去掉扶手”。
- 评审不认证木材种类、承重或结构安全；这些只能说“图片无法确认”。
- 智能体在以下情况停止：通过（`passed`）、到达轮数（`round_limit`）、连续两轮没有改善（`no_improvement`）、评审出错或不完整、生图出错、用户停止。第二轮起以上一版图片为输入修改。

评测报告把生图失败、评审失败、评审不完整、违反需求、风格不符分开计数；未知不算 0，比例只在已知值上计算（`scripts/evalStyle.js`）。

## 6. 模型能力

每个适配器通过 `capabilities()` 如实声明能力，`GET /api/v1/capabilities` 返回给前端。状态：`verified`（本项目实测）、`image_conditioned`（以图片为条件重新生成）、`documented_unverified`（官方文档有、本项目未实测）、`unsupported`。

| 能力 | Codex CLI | 图像模型（OpenAI 兼容） | Gemini | A1111 / ComfyUI |
| --- | --- | --- | --- | --- |
| 参考图 | 已实测，最多 3 张（`-i`） | 文档有，未实测（`/images/edits`） | 文档有，未实测 | 不支持 |
| 以上一版为输入修改 | 以图片为条件重新生成，不是像素级编辑 | 文档有，未实测 | 文档有，未实测 | 不支持 |
| 多轮对话 | 不支持（每次 `--ephemeral`） | 不支持 | 不支持 | 不支持 |
| 局部（蒙版）编辑 | 不支持 | 不支持（未接入蒙版） | 不支持 | 不支持 |
| 中间预览 | 不支持（CLI 不输出中间图） | 不支持 | 不支持 | 不支持 |

Codex CLI 仍是首选引擎，模型与推理强度沿用现有配置。Gemini 只有在 `GEMINI_API_KEY` 与 `GEMINI_IMAGE_MODEL` 都配置时才出现在引擎列表。

### 真实模型验证（2026-10-14，本机 Codex CLI 0.162.0，GPT-6.1 Sol / high）

用 `scripts/verifyEngines.js` 走工作台同样的任务路径，需求为“一把无扶手的新中式餐椅，全金属，不要木头”，细化要求为“保留这把椅子，背板更薄，坐垫换成黑色皮革”。生产 CLI 为 0.159.2，未在生产上重复验证。

| 步骤 | 耗时 | 结果 |
| --- | --- | --- |
| 生成第一版 | 73 秒 | 无扶手、全金属、无木材 |
| 四项评审 | 56 秒 | 通过，86 分；13 项锁定需求都有视觉证据；古旧风险 15 |
| 以上一版为输入细化 | 82 秒 | 坐垫换成黑色皮革，框架、背板、机位、背景保持不变 |
| 一致性评审 | 62 秒 | 没有未要求的改动；“背板更薄”判为无法判断（图上看不到板厚） |
| 三视图（3 张 + 3 次评审） | 460 秒 | 正视通过；侧视接近正侧面，俯视是高角度斜视，不是正投影，两张都被评审判为“需修改”；设计本身前后一致 |

结论：

- **参考图（含上一版图片）**：实测有效，细化时附 1 张上一版图片（`-i`）。
- **以上一版为输入修改**：实测形体、机位和背景保持得很好，但仍是重新生成，不是像素级编辑。一次早先的运行里背板颜色从深灰变成亮银，一致性评审把它列为“未要求的改动”。
- **评审**：四项评审的结构化结果完整可用；能指出未执行的修改和未要求的改动。
- **中间预览**：CLI 只输出 `thread.started`、`turn.started`、`item.completed`（`agent_message`，以及一条关于开发中功能开关的提示）和 `turn.completed`，没有任何中间图片事件，因此不支持。
- **用量**：生成一次约 4–6 万输入 token（大部分命中缓存）、500–800 输出 token；每次评审单独调用一次。

验证中发现并修复了两个问题：细化时“坐垫换成皮革”仍被“全金属”判为违规；细化时方向里的材料仍写着“全金属”。两处都已加回归测试。

## 7. 版本与三视图

每次生成都写入设计会话（`HISTORY_DATA_DIR/sessions/`），记录需求、方向、参考及用途、改动范围、模型、评审摘要和停止原因。结果面板可以勾选两个版本对比，也可以恢复早先的版本；恢复后的版本成为下一次细化的基础。

“三视图”以当前版本为输入，生成正视、侧视、俯视三张**概念示意图（不是工程图纸）**，每张都与原版本做一致性评审。

## 8. 接口

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/v1/design/brief` | 预览结构化需求与默认方向（不生成） |
| `POST /api/v1/design/directions` | 三个候选方向与匹配案例 |
| `GET /api/v1/capabilities` | 各引擎能力声明 |
| `GET /api/v1/real-cases` | 真实案例库，可按 `category`、`style` 过滤 |
| `GET /api/v1/design-sessions`、`GET /api/v1/design-sessions/:id` | 当前账号的设计会话与版本 |
| `POST /api/v1/design-sessions/:id/restore` | 恢复某一版本 |
| `GET/POST /api/v1/references`、`PATCH/DELETE /api/v1/references/:id`、`GET /api/v1/references/:id/file` | 当前账号的参考资料 |
| `POST /api/v1/generation-tasks` | 生成任务；`action` 为 `new` / `variation` / `newDirection` / `refine` / `views` |

全部需要登录，并按账号隔离；凭据只在服务器上。文档下载以附件形式返回，带 `nosniff`。

## 9. 数据与部署

- `USER_REFERENCE_DIR`：用户上传，默认 `data/user-references`，Docker 中为 `/app/data/user-references`。
- 设计会话在 `HISTORY_DATA_DIR/sessions/`，随历史一起备份。
- 两者都是私有数据，不进 Git、不进镜像。

## 10. 评测

固定评测集 `eval/design-briefs.json`：

- `dev`：开发过程中用过的需求，可以据此调试。
- `holdout`：只用于对比，不能据此调整提示词、知识或规则。
- `mock: true` 的用例（冲突参考、评审缺字段、网络失败）由自动化测试用本地替身覆盖，不用真实模型跑。
- 每条用例的检查项是人工写的，不依赖需求解析器，任何版本都能用同一套检查评。

`node scripts/verifyEngines.js --engine codexCli --out <目录> [--views]` 走工作台同样的任务路径，用真实模型验证：生成 → 评审 → 以上一版为输入细化 → 一致性评审 →（可选）三视图，记录耗时、用量和 CLI 事件类型。会调用真实付费模型；把 `HISTORY_DATA_DIR` 指向输出目录，避免写入真实历史。
